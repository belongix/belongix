What system design interviews actually test
10 min

System design interviews are not about perfect answers — they test how you think through ambiguous, large-scale problems. Interviewers want to see structured thinking, awareness of trade-offs, and the ability to communicate clearly.

Who gets asked system design questions

  • SDE-2 and above at product companies
  • Freshers at FAANG (simplified versions)
  • Any senior+ role at startups

The 5-step framework (use every time)

  1. Clarify requirements (5 min) — users, scale, SLA, features
  2. Define the API (5 min) — what endpoints/interfaces
  3. High-level design (10 min) — boxes and arrows
  4. Deep dive (15 min) — one component in detail
  5. Identify bottlenecks + trade-offs (5 min)

  • I've memorised the 5-step framework

Scalability fundamentals — what every interview assumes you know
20 min

The core concepts

Horizontal vs Vertical Scaling: Vertical = bigger machines (limited). Horizontal = more machines (preferred for large scale).

Load Balancing: Distributes traffic across servers. Common: Round-robin, Least-connections, IP-hash. AWS ALB / Nginx are the go-to examples.

Caching: Store frequently accessed data in memory. Redis is the standard answer. Cache strategies: Cache-aside, Write-through, Write-back. Always discuss: what to cache, TTL, cache invalidation.

CDN: Serve static assets (images, JS, CSS) from servers geographically close to users. Mention: Cloudflare, AWS CloudFront.

Database Sharding: Split data across multiple DB instances by a shard key. Discuss: shard key selection, hotspot problem.

Replication: Primary-replica setup. Reads go to replicas, writes to primary. Lag is a trade-off.

💡 Interview tip: Mention CAP theorem when discussing distributed systems — Consistency, Availability, Partition tolerance. Every distributed system can only guarantee 2 of 3.

  • I can explain load balancing and when to use it
  • I can explain Redis caching with cache-aside pattern
  • I can explain database sharding and its trade-offs

Design a URL shortener (Bit.ly) — your first practice
25 min

Most commonly asked. Know this cold.

Step 1 — Requirements:
Functional: Given long URL → return short URL. Short URL → redirect to long URL.
Non-functional: 100M URLs created/day. Read-heavy (100:1 read:write ratio). Low latency (<10ms). High availability.

Step 2 — API Design:
POST /shorten { long_url } → { short_url }
GET /{short_code} → 301/302 redirect

Step 3 — High-level design:
Client → Load Balancer → App Server → (Redis Cache + PostgreSQL DB) + Base62 encoder

Step 4 — Deep dive: Short code generation:
Option A: MD5 hash → take first 7 chars. Problem: collisions.
Option B: Auto-increment ID → encode to Base62 (a-z, A-Z, 0-9). 7 chars = 62^7 = 3.5 trillion URLs. This is the standard answer.

Step 5 — Bottlenecks:
DB read bottleneck → cache short:long URL mapping in Redis with LRU eviction.
Single DB → read replicas. Eventually consistent for analytics OK.

  • I can design a URL shortener from scratch in 35 minutes
  • I understand Base62 encoding

Design Instagram Feed — intermediate level
30 min

The feed generation problem — core to understanding distributed systems

Requirements:
Post photos, follow users, see home feed (chronological + ranked).
Scale: 1B users, 100M daily active, 500M posts/day viewed.

The key design decision: Push vs Pull for feed generation

Pull (fan-out on read): When user opens app, query all followees' posts. Merge and sort. Problem: slow for users following 10,000+ people.

Push (fan-out on write): When user posts, push to all followers' feed lists (stored in Redis). Problem: celebrities with 10M followers → 10M writes per post.

Hybrid (what Instagram actually uses): Push for regular users, pull for celebrities. Threshold: 10,000 followers = pull.

Storage: Images → S3/object store → CDN for delivery. Metadata → Cassandra (write-heavy, distributed, no joins needed).

📌 Pro tip for interviews: The interviewer wants to see you identify the celebrity/hot user problem and propose a hybrid solution. This one insight separates average from strong candidates.

  • I can explain push vs pull for news feed generation
  • I understand the hybrid approach for celebrity users

Message queues, rate limiting, and other must-know patterns
20 min

Message Queues (Kafka, SQS)

Use when: async processing needed, decoupling producer from consumer, handling traffic spikes. Example: User uploads video → queue → async transcoding job. Kafka: high-throughput, persistent, replayed. SQS: simpler, managed.

Rate Limiting

Prevents abuse. Algorithms: Token Bucket (smooth bursts allowed — standard answer), Fixed Window, Sliding Window. Implementation: Redis + Lua script for atomic counter decrement.

Consistent Hashing

Used for distributing data across cache nodes without full rehashing when nodes join/leave. Add virtual nodes for even distribution.

SQL vs NoSQL decision framework

Use SQL when: ACID needed, complex queries, relationships. Use NoSQL when: high write throughput, flexible schema, horizontal scale. Common: Cassandra (write-heavy time-series), MongoDB (documents), DynamoDB (key-value, AWS-native).

  • I can explain token bucket rate limiting
